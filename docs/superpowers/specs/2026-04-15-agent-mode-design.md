# 结构求解器 Agent 模式设计

## 背景与目标

当前求解器已经具备参数化建模、荷载编辑、矩阵位移法求解和结果展示能力，但用户仍需通过左侧参数面板、拖拽和表单逐项操作。现有 AI 能力主要以独立聊天窗口存在，没有深入进入求解器主工作流。

本次设计的目标是在 `SolverModule` 中增加一个真正可操作的 Agent 模式，让用户可以用自然语言：

- 新建现有参数化结构模型
- 反复修改几何、材料、支座和荷载
- 基于当前求解结果发起追问并获得解释
- 在不破坏现有手动建模流程的前提下，把自然语言变成可靠、可确认、可撤销的结构化操作

首期明确范围：

- 入口放在求解器右侧结果区上方，采用对话面板形态
- 支持自然语言优先、必要时回退为半结构化确认
- 支持现有参数化结构类型，不做自定义节点/单元的自然语言创建
- 支持五类高频指令：新建模型、修改几何与材料、管理荷载、修改支座/约束、解释结果
- 结果解释深度到“事实 + 工程语义解释”，不包含自动设计优化建议
- 采用“本地规则 + 大模型”混合解析，不允许大模型直接改写求解器状态

非目标：

- 不在首期实现自定义结构自由建模的自然语言输入
- 不在首期实现截面优化、方案优化或自动设计建议
- 不重构现有求解核心 `solveStructure` 与几何生成核心 `generateGeometry`
- 不替代现有左侧控制面板、几何编辑器和拖拽交互

## 用户体验概览

用户进入求解器后，右侧顶部看到新的 `AgentPanel`。用户可以像聊天一样输入工程口语，例如：

- “建一个三跨连续梁，跨长都 6 米”
- “在第二跨跨中加 20kN 向下集中力”
- “把左端改成固支，右端还是滚支”
- “为什么这里弯矩最大？”

Agent 处理流程如下：

1. 解析用户输入，提取结构化意图与动作列表
2. 生成一段简洁的理解摘要
3. 对低风险高置信度操作直接应用到当前求解器状态
4. 对高风险或歧义操作展示确认卡，待用户确认后再执行
5. 求解器自动重新计算，并把新结果回传给 Agent
6. Agent 在数值事实的基础上补充工程语义解释

用户仍可继续使用左侧参数面板或画布交互。Agent 看到的永远是当前真实模型状态，而不是只依赖聊天记录。

## 整体架构

Agent 模式在架构上是“自然语言控制层”，而不是新的求解内核。`SolverModule` 继续持有唯一真实状态：`params`、`nodes`、`elements`、`loads` 和 `results`。Agent 只负责把自然语言转成结构化动作，再通过本地执行层安全地修改状态。

建议新增以下模块：

- `components/solver/AgentPanel.tsx`
  - 对话 UI、输入框、消息列表、操作摘要卡、确认按钮、撤销按钮
- `utils/agent/types.ts`
  - Agent 意图、动作、风险等级、确认卡、执行结果等类型定义
- `utils/agent/parser.ts`
  - 解析入口，负责编排规则解析与大模型解析
- `utils/agent/ruleParser.ts`
  - 本地规则抽取：结构类型、跨数、层数、荷载类型、量纲、支座词汇、位置词
- `utils/agent/llmParser.ts`
  - 大模型补全歧义语义，返回受约束的 JSON 意图
- `utils/agent/session.ts`
  - 保存本轮会话上下文，如最近提到的荷载、跨号、支座、结构对象
- `utils/agent/risk.ts`
  - 判断动作是否直改、是否需要确认
- `utils/agent/executor.ts`
  - 将动作映射到 `SolverParams` 草案，校验后原子提交
- `utils/agent/explainer.ts`
  - 基于 `AnalysisResult` 生成事实摘要和工程语义解释
- `utils/agent/modelSummary.ts`
  - 生成当前模型摘要，供 Agent 理解当前状态与回显给用户

推荐的数据关系如下：

`AgentPanel -> parser -> risk -> executor -> SolverModule state -> solveStructure -> explainer -> AgentPanel`

## 交互与风险分级设计

`AgentPanel` 位于结果区上方，默认展开。面板内部包括四个区域：

- 对话区：显示用户消息、Agent 的理解、执行反馈、结果解释
- 输入区：自然语言输入框与发送按钮
- 摘要卡区：展示本次识别出的结构、对象和待执行操作
- 快捷动作区：确认执行、撤销上一步、查看当前模型摘要、清空对话

### 风险分级

低风险，可直接应用：

- 单个参数微调，例如跨长、层高、`E`、`A`、`I`
- 单个荷载增删改
- 单个支座类型修改
- 只读问题，例如“最大位移是多少”“哪个杆件最危险”

中风险，通常确认：

- 一次修改多个关键参数
- 结构类型切换但尝试保留部分现有设置
- 删除多项荷载
- 几何变化导致现有荷载或支座映射关系可能失效

高风险，必须确认：

- 用新结构覆盖当前模型
- 清空全部荷载或重大重建动作
- 指令本身歧义较大，但影响范围很大
- 解析置信度不足且存在多个合理候选解释

### 确认卡信息

确认卡至少应包含：

- Agent 当前理解的结构或目标对象
- 待执行动作列表
- 影响范围说明
- 是否会覆盖当前模型
- 主操作：确认执行
- 次操作：改用另一种理解/改用半结构化确认

### 半结构化回退

当自然语言存在多解时，Agent 不强行猜测，而是回退到更确定的确认路径。例如：

- “在中间加个荷载” -> 明确是跨中、整体中心还是某根杆件中心
- “支座改一下” -> 明确是哪个支座、改成什么类型
- “换成框架” -> 明确是门式刚架还是多层多跨框架

## 自然语言解析设计

解析采用“规则优先 + 大模型补全 + 本地归一化”的混合链路。

### 第 1 层：本地规则预解析

本地规则负责识别高确定性、低歧义的信息：

- 结构类型：简支梁、连续梁、门式刚架、多层多跨框架、桁架、悬臂、人字刚架
- 拓扑参数：跨数、层数、跨长、层高、屋脊高度
- 材料参数：`E`、`A`、`I`、刚度假设
- 荷载类型：集中力、分布荷载、力矩
- 荷载大小与方向：`20kN`、`12kN/m`、向下、水平向右
- 支座类型：固支、铰支、滚支、水平滚支、竖向滚支
- 常见位置词：跨中、1/3 跨、第二跨、左端、右端、柱顶、梁端

### 第 2 层：大模型补全语义

大模型负责处理规则难稳定覆盖的表达，例如：

- “把它改成门式刚架”
- “刚才那个集中力再大一点”
- “在第二跨靠右一点加个荷载”
- “为什么这一层的柱子更危险”

大模型输出必须是受约束的结构化 JSON，而不是直接返回代码或最终状态。建议其输出只包含：

- `intent`
- `actions`
- `references`
- `confidence`
- `needsConfirmation`
- `reasoningSummary`

### 第 3 层：本地归一化与校验

无论信息来自规则还是大模型，都必须经过本地归一化：

- 单位统一为内部使用格式
- 口语位置映射为标准字段，如 `targetSpan=2`、`location=0.5`
- 检查对象是否存在
- 检查参数是否越界或缺失
- 检查动作是否与当前结构类型兼容

### 第 4 层：生成结构化动作

首期动作集合固定为：

- `create_structure`
- `update_geometry`
- `update_material`
- `add_load`
- `update_load`
- `remove_load`
- `update_support`
- `explain_results`
- `summarize_model`
- `undo_last_agent_action`

动作对象推荐只表达“意图”和“目标”，不携带整份 `SolverParams`，以便执行层做最终决定。

## 会话上下文设计

为支持连续对话，需要引入轻量的 `AgentSession`。它不替代真实模型状态，只补充对话中的指代消解。

建议记录：

- 最近一次被操作的结构类型
- 最近一次被提及的荷载 ID 或语义标识
- 最近一次被提及的跨号、层号、杆件、节点
- 最近一次结果关注点，如最大弯矩、最大位移、某根杆件
- 最近一次执行摘要

这样可以支持诸如以下连续操作：

- “在第二跨跨中加 20kN”
- “把它改成 30kN”
- “再往右移一点”
- “为什么改完以后这里更危险了？”

## 执行层设计

执行层的原则是：Agent 不直接写 `setParams`，而是先产出“下一状态草案”，校验通过后再原子提交。

### 执行流程

1. 复制当前 `params` 生成工作草案
2. 依次执行动作列表
3. 对草案做统一校验
4. 校验通过后一次性提交给 `setParams`
5. 记录快照用于撤销
6. 触发现有求解链路重新计算结果

### 为什么要原子提交

一条自然语言可能包含多个连贯动作，例如：

- “改成三跨连续梁，并在第二跨跨中加 20kN 向下集中力”

正确执行顺序必须是：

1. 重建结构类型与参数
2. 根据新结构定位第二跨
3. 在新几何上创建荷载

如果边修改边渲染，容易产生中间态错误或错误映射。

### 不同动作的执行策略

`create_structure`
- 只允许生成首期支持的参数化结构
- 通过结构类型和参数落回现有 `generateGeometry`
- 不允许大模型自行拼接节点与单元

`update_geometry` / `update_material`
- 直接修改参数字段
- 多字段联动时统一进入草案校验
- 结构变化后需要检查既有荷载能否继续映射

`add_load` / `update_load` / `remove_load`
- 推荐在现有 `Load` 基础上增加 Agent 语义定位信息，例如内部维护一个补充索引，帮助识别“刚才那个集中力”
- 如果荷载因结构变化无法映射，不能静默丢失，应进入确认或报错

`update_support`
- 将工程语言支座类型映射到节点 `restraints`
- 首期仅支持参数化结构的关键支座点修改，不开放任意节点自由约束的自然语言编辑

### 撤销机制

每次 Agent 成功执行前都保存一份快照：

- `params`
- 本次执行摘要
- 时间戳

当用户点击“撤销上一步 Agent 操作”时，恢复上一份 Agent 快照。撤销范围只覆盖 Agent 发起的改动，不试图做全局时间旅行。

## 结果解释设计

结果解释采用“两层回答”：

### 事实层

尽量由本地直接回答，保证数值准确：

- 最大位移是多少
- 最大弯矩、剪力、轴力在哪里
- 哪个节点反力最大
- 哪个杆件内力最不利

这一层只依赖 `AnalysisResult`、当前结构和荷载状态，不需要大模型生成数值。

### 工程语义层

在事实层提取完关键数据后，再由大模型组织自然语言解释：

- 为什么跨中弯矩最大
- 为什么某个支座反力增大
- 为什么这一层柱子更危险
- 荷载路径和受力特点如何理解

大模型只负责表达，不负责虚构数值。提示词中必须显式要求：

- 只能引用本地提供的数值事实
- 不得编造新的结果
- 表达控制在简洁、教学式、工程语义清楚的范围内

## 错误处理与降级策略

执行失败时，不更新状态，只向面板返回结构化错误，再由 Agent 转成可读提示。

常见失败场景：

- 当前结构不存在用户提到的“第二跨”
- 新结构建立后原荷载找不到可映射位置
- “中间支座”无法唯一定位
- 参数单位或数值非法
- 模型求解出现奇异矩阵或约束不足

降级策略：

- 解析失败 -> 回退为半结构化确认
- 大模型不可用 -> 仅保留规则解析与事实型结果问答
- 解释型问题无法生成语义回答 -> 至少返回事实型摘要
- 求解失败 -> 面板给出错误诊断，不丢失当前对话上下文

## 测试策略

当前项目没有正式测试框架，但本次功能必须至少具备可验证的最小测试闭环。

### 单元测试优先对象

如果引入测试框架，优先覆盖以下纯函数：

- `ruleParser`
- `risk` 分级判断
- `executor` 的动作映射与草案生成
- `modelSummary`
- `explainer` 的事实层提取

### 无框架情况下的最低验证要求

- 使用 `npx tsc --noEmit` 做类型检查
- 为解析器和执行器保留可独立调用的纯函数，便于后续补测
- 手工验证至少覆盖以下场景：
  - 新建一个参数化结构
  - 增加、修改、删除单个荷载
  - 修改支座类型
  - 修改几何参数后重新求解
  - 连续两轮对话中的指代消解
  - 歧义输入触发确认卡
  - 求解异常时返回清晰诊断
  - 撤销上一条 Agent 操作

## 分阶段实施建议

### Phase 1：最小可用闭环

- 新增 `AgentPanel`
- 接入当前模型摘要
- 实现规则解析 + 动作执行 + 风险确认
- 支持五类核心指令中的高频路径
- 支持事实型结果问答

### Phase 2：大模型增强

- 引入 `llmParser`
- 接入连续对话上下文
- 增强歧义消解与工程语义解释
- 增加半结构化确认卡

### Phase 3：体验完善

- 撤销与会话历史优化
- 荷载语义索引增强
- 更丰富的模型摘要与解释模板
- 更细的错误诊断与提示

## 成功标准

首期实现完成后，应满足以下标准：

- 用户可以通过自然语言完成现有参数化结构的创建与修改
- 用户可以通过自然语言管理荷载与关键支座
- 用户可以基于当前求解结果发起连续追问
- 低风险操作可直接执行，高风险操作会先确认
- Agent 操作不会绕开本地校验直接改写状态
- 执行失败时模型状态保持稳定
- 至少支持一步撤销
- 在大模型不可用时，仍可保留基础规则解析与事实问答能力

## 待实现原则总结

本设计的核心原则是：

- 大模型负责理解语言，不负责直接写状态
- 本地执行层负责安全、可校验、可回滚的状态变更
- `SolverModule` 仍然是唯一真实状态源
- Agent 是自然语言入口，不是新的求解器
